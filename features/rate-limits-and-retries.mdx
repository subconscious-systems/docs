Use **`Retry-After`** (and the matching fields in the error payload, when your protocol exposes them) to backoff when `https://api.subconscious.dev` throttles or asks you to wait. This page describes **what callers see** on the public API.

<Note>
Per-model limits are advertised on [`GET /v1/models`](/api-reference/models). See [Model discovery](/features/model-discovery) for partner catalog integration.
</Note>

## Endpoints

- `POST /v1/chat/completions`
- `POST /v1/messages`
- `POST /v1/responses`

On **JSON error responses** (failures before a stream starts), all three set the **`Retry-After`** header when a wait time is known.

| Route | Header | `retry_after_seconds` on JSON errors |
|-------|--------|--------------------------------------|
| Chat Completions | Yes | `error.details.retry_after_seconds` |
| Responses | Yes | Same OpenAI-style `error` object |
| Messages | Yes | Not on JSON errors — use the **header** (SSE mid-stream errors can include `error.details`) |

## Header format

- **Name:** `Retry-After`
- **Value:** non-negative integer **seconds**
- Limit rejections use delay-seconds, not HTTP-date

## How the wait time is computed

When a **configured limit** blocks the request, the API returns **HTTP 429** and sets `Retry-After` to the **remaining time until that limit’s usage counter resets** (minimum 1 second). The JSON field `error.details.retry_after_seconds` matches the header where that object is returned.

Counters use Redis TTL semantics:

- **Minute, hour, day:** **Rolling** windows. The window starts when the counter is first touched; it expires after 60s, 3,600s, or 86,400s respectively. `Retry-After` is the **seconds left on that expiry** — typically less than the full window if you were throttled partway through.
- **Month:** **Calendar** month in UTC (`YYYY-MM`). The counter resets at **00:00:00 UTC** on the first day of the next month.

| Limit window | `error.code` |
|--------------|--------------|
| `minute`, `hour` | `rate_limited` |
| `day`, `month` | `quota_exceeded` |

`error.type` is `rate_limit_error` for both on Chat Completions and Responses. Details may include `scope` and `current_usage`.

### Entitlement suspended

**HTTP 403**, code `entitlement_suspended`. **No `Retry-After`** — access must be restored on the account side; backoff alone will not help.

## Streaming

| Failure timing | HTTP `Retry-After` | Where to read seconds |
|----------------|-------------------|------------------------|
| Before stream bytes | Yes | Header; plus JSON details on Chat/Responses |
| After stream started | No (response already `200` + SSE) | Terminal stream error event |

Rejected limit checks are not metered as successful completions.

## Client recommendations

1. Sleep at least `Retry-After` seconds (with jitter) before retrying on **429**.
2. Expect longer waits for `quota_exceeded` than `rate_limited`.
3. Do not auto-retry `entitlement_suspended`.
4. When other retryable API errors include `Retry-After` or `retry_after_seconds`, honor them the same way.

Responses with no delay field (typical 400/401/500) need your own backoff policy.
