On **429**, read **`Retry-After`** (seconds, minimum 1) before retrying. Same timing appears as `error.details.retry_after_seconds` where that object is returned (not on Anthropic JSON errors — use the header).

<Note>
Limits per model: [`GET /v1/models`](/api-reference/models). **429** response headers are in [openapi.json](/api-reference/openapi.json) under `components.headers`. Partners: [Model discovery](/features/model-discovery).
</Note>

## Routes

`POST /v1/chat/completions`, `/v1/messages`, `/v1/responses`.

| Route | JSON field |
|-------|------------|
| Chat Completions, Responses | `error.details.retry_after_seconds` |
| Messages | Header only on JSON errors |

## What the delay means

Configured limits return **429** with `Retry-After` = **remaining time until that counter resets** (rolling window for minute/hour/day; calendar UTC month for month).

| Window | `error.code` |
|--------|----------------|
| minute, hour | `rate_limited` |
| day, month | `quota_exceeded` |

**403** `entitlement_suspended` sends **no** `Retry-After`.

## Streaming

Errors **before** stream bytes: JSON response + header. **After** bytes: no header; delay only in the stream error event.

## Clients

Backoff at least `Retry-After` on **429**; do not retry **403** suspension. Limit rejections are not metered as completions.
